You are working in the repository:

https://github.com/tobystrings/industrial-asset-graph

Product: Industrial Asset Graph — J. Lieb Foods facility knowledge system.

MISSION

Evolve the current high-quality, single-technician, map-first cabinet/documentation tool into a plant-wide living asset graph that can safely scale to hundreds or thousands of assets and multiple technicians without sacrificing the project's evidence discipline, field usability, existing 2D visual identity, or current working demo.

This is an evolution of the existing product, not a rewrite.

The final architecture and product must provide:

1. A scalable, versioned facility graph data model.
2. A shared multi-user source of truth with excellent offline field capability.
3. Real evidence-backed relationship population and graph traversal.
4. A technician-friendly Draft → Review → Canonical workflow.
5. Clear local/save/sync/conflict state feedback.
6. Plant-scale search, filtering, health/coverage, and verification workflows.
7. Strong accessibility, responsive behavior, error handling, and visual regression protection.
8. A safe migration path from all current FacilityPackage / IndexedDB / .iag data.

ABSOLUTE HONESTY RULE

Never invent plant facts.

Do not invent equipment, machines, motors, HP, wiring, destinations, feeds, controls, sensors, interlocks, LOTO steps, surveyed locations, upstream/downstream paths, relationship instances, or any other facility fact.

Unknown information must remain unknown or be explicitly represented as FIELD_VERIFY, INFERRED, DISPUTED, or another existing evidence state as appropriate.

Do not populate relationship instances merely because the new schema supports their relationship types.

Do not create fake J. Lieb facility data simply to make a new graph view look populated.

Synthetic fixtures are allowed only for testing scale/performance and must be clearly separated from canonical facility truth.

PHASE 2 — SHARED SOURCE OF TRUTH + OFFLINE SYNC
==================================================

Implement the simplest robust multi-user architecture appropriate for this repository.

PREFERRED V1 DIRECTION

Unless the repository audit reveals a strong reason otherwise, prefer:

- central backend API
- PostgreSQL as the canonical shared store
- IndexedDB retained as the offline/local cache
- IndexedDB or equivalent local outbox/mutation queue
- optimistic concurrency using entity version/base revision
- stable actor/user/device identity
- server-side audit trail
- explicit conflict detection
- WebSocket or SSE only where it provides clear value
- portable .iag import/export retained as backup/handoff

Do NOT introduce CRDT complexity by default.

Use a CRDT or third-party sync engine only if the audit demonstrates that field-level collaborative editing genuinely requires it and the added operational complexity is justified.

Do NOT introduce Neo4j merely because this is called a graph.

A relational canonical store with indexed node/edge tables and recursive graph queries is acceptable and preferred unless measured requirements prove otherwise.

BACKEND DEVELOPMENT EXPERIENCE

Make the backend easy to run locally.

A Docker Compose development path for PostgreSQL is acceptable.

Keep the public GitHub Pages demo capable of running in read-only/seeded/local mode without requiring the private production backend.

The frontend should have a clear persistence/data-service abstraction so GitHub Pages demo mode, local/offline mode, and shared-backend mode do not require scattered conditionals across UI components.

SYNC MODEL

Implement a real synchronization contract.

Do not relabel the existing ID-based .iag/import merge as multi-user synchronization.

A client mutation should carry enough information to safely detect stale or duplicate edits, such as:

- mutation ID
- entity ID
- entity type
- actor ID
- device/client ID
- base entity version
- operation
- timestamp
- changed fields or patch
- verification/review metadata when relevant

The server must either:

- accept the mutation and return the new canonical version, or
- reject/flag it as a conflict with enough information for the UI to resolve it.

Mutations must be idempotent so retries do not create duplicate changes.

OFFLINE

A field technician must be able to:

- open previously cached facility data
- capture observations
- create draft assets/components/relationships
- attach LOCAL_ONLY evidence
- continue working without network access
- clearly see what is saved locally
- clearly see what is pending synchronization
- reconnect later
- sync eligible changes without losing data
- review conflicts created while offline

LOCAL_ONLY TRANSPORT INVARIANT

LOCAL_ONLY evidence must be excluded from automatic upload at the sync boundary itself.

Do not rely only on hiding it in the UI.

The synchronization layer must have an explicit automated test proving LOCAL_ONLY attachments/evidence are not transmitted unless the user deliberately promotes them through the approved workflow.

IDENTITY

Create a practical v1 identity model with:

- user ID
- display name
- role
- device/client identity

Design for roles such as:

- viewer
- field technician
- engineer
- admin

A prototype may use simplified local/development authentication, but do not represent display-name-only identity as production-grade security.

Keep authentication boundaries replaceable and document what is and is not secure in v1.

AUDIT

Canonical shared changes must preserve:

- who changed it
- when
- previous version
- new version
- reason/evidence where relevant
- review/approval information where relevant

CONFLICT UX

Implement at least one real end-to-end conflict scenario.

Example:

Technician A and Technician B edit the same canonical fact from the same base version.

The second incompatible update must not silently overwrite the first.

Surface:

- current canonical/server value
- technician's attempted value
- verification state
- evidence/provenance
- author
- timestamp
- base revision
- current revision

Allow an explicit resolution action.

Never automatically resolve safety-, evidence-, or plant-truth-relevant conflicts by last-write-wins.
